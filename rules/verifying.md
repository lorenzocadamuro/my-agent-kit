## Verify, don't assume

- **Check every claim against the code or the data** before it shapes a decision or reaches the user, including claims made by other agents, the user's own proposals, and your own: a ticket's premises, live state (flags, config, the environment, a preview), the consequences written into a question's options and the premise its recommendation rests on (a production volume or frequency is measured with a read-only query, or the recommendation says it is unverified and which measure would decide it), and "done", "it is live" or "it works". Each one carries its evidence (`file:line`, a read-only query, a measurement in the page) or is marked unverified. An audit's claim about behaviour is reproduced, or marked "text only" and fixed in text. Every text that reports a result or proposes a change, in chat or in a file, yours or dictated to an agent (a plan, a question, a summary, a triage's text for the executor, a comment draft, a row a round defers), is checked claim by claim against its source before it is reviewed or shown: each claim names the run or the read that showed it and says only what that run exercised; a fix proposed for adoption (a change of scope, a patch) says whether it ran against the tests of its area, or says "not run"; when the proof is partial, the text claims less instead of summarising more; a claim about an outside source (a comment, a ticket, a doc) is quoted from it as read now, and absolute or causal words (none, always, comes from) stay within what the evidence shows. When the user says what they see (the chat's language, a missing explanation, a screen), check it against the session record (transcript, files, screenshots) before answering; never contradict it from memory.
- **Audits are never truncated.** Report the match count and every hit.
- **Run it, and measure the baseline, before relying on it.** Every tool, client or command the plan relies on, or the kit hands to the user, runs once for real first (in the same folder and project; a dry run or a dummy value for a secret), and its prerequisites (access, environment) and measured duration go with it into the plan or the message. A command that changes shared state (production config, deploys, data, anything published) is tried only as a dry run or its read-only part; otherwise it is marked "not tried" and the user is told. A command enters the bar for done or a stop condition only after it ran on `origin/main`. If it already fails there (a missing tool, a known failure), write it as "no new failures against the baseline", with the baseline counts.
- **A test or a check must be able to fail.** Drive the production caller, up to the real consumer (the client that will call it, not only its handler), in the shape the guide or the plan tells users to write it (an adopter built as the guide says, not only an inline case), and check that reverting the fix makes the test fail. A check enters the bar for done only after it was seen failing on the change's likeliest wrong inputs (a misspelled name, a missing key), alone and, when one check guards several rules, together, or its code shows it checks that; otherwise say it cannot fail, and look for one that can. An intermittent defect is captured first (temporary instrumentation, a trace of the failing repetition), before any hypothesis.
- **The writer is not the reviewer.** Reviews run in a fresh context that did not write the code.
- **Stop and report** when the code contradicts the plan, instead of improvising. Never relax a check or a stop condition (the plan's, the round's, your own) without the user's yes: skipping it, running it less often or turning it into a ticket is a gate; one that fires goes to the user. A check with a noisy result (an LLM judge, a model's choice) runs 2–3 times before it is called passed or failed.
